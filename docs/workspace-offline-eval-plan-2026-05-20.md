## 0. 这次测试要回答 3 个问题

1. **功能完整性**:刚做的 5 个模块(档案 / plan-mode / 推荐反馈 / 改写 / 三栏布局),学生从打开网页到关闭网页,**每个都能摸到、每个都能用完**。任何一处断链就算 fail。

## 2. 每个 persona 跑完的完整脚本(模拟真实学生 1 次完整 session)

每个 persona 跑一遍下面 7 步,**全程不许人工介入**:

### Step 1 — 上传简历 + 自动 parse
- 用 persona 生成的 PDF / 文本上传
- 验证:parse 出来的实习 / 项目 / 技能数 ≥ persona 实际条数 90%

### Step 2 — 首次进档案
- 调 `GET /memory`,验证档案被 parse 自动填了 N 条 experience entries(A-7)
- 验证:绿点 🟢 在 UI side 应该亮(本测试不渲染 UI,只验数据流)

### Step 3 — chat 互动 5 轮(模拟学生主动追加细节)
- 让 persona AI 按"沟通风格"扮演学生,跟 chat 系统聊 5 个 message
- 内容:补充某段实习的细节 + 问一个简历改写的问题 + 透露一个偏好(想去上海 / 不想去某行)
- 验证(A 模块):
  - 每一轮后调 `GET /memory`,看新增 entry 数
  - 抽取的 category 必须 ∈ {experience, skill_claim, preference} (A-4 简)
  - 透露的偏好应当生成 preference entry
  - **同一事实第二次说,不应重复入档**(dedupe)

### Step 4 — 触发 plan-mode 深聊某段经历
- 切换到 plan-mode
- 选 persona 的一段实习经历(focus_kind=experience + focus_id)
- AI 反问 → persona 回答 → 最多 6 轮
- 验证(B 模块):
  - 4-anchor 进度(时间 / 行动 / 工具 / 结果)是否在 ≤6 轮内全 ✓
  - finalize 后草稿 summary 长度 ≥ 100 字
  - 学生"入档"后,该条 experience 在 archive 里能找到

### Step 5 — 拿到推荐 + 反馈 1 条
- 调 `GET /recommendations` 拿 top 10
- 验证(D 模块):
  - 数量 ≥ 1(50 分门槛后可能 < 10,接受)
  - 每张卡都有 "为什么推" 字段且非空
  - 每张卡都有 ≥ 1 条 ✓ 强匹配 bullet
- persona 选 1 张推荐卡 ✗ reject(reason 跟 persona 偏好对应)
- 验证:
  - `POST /reject` 返 200
  - 档案多一条 preference
  - 再次 `GET /recommendations`,该 job 已不在列表

### Step 6 — 改写 3 条 bullet(测 thesis + 防编数字 + 老师 top 3 痛点)

每个 persona 选 3 条 bullet 测,**3 条要覆盖不同测试目的**:

1. **第 1 条 — "流水账实习段"**(每个 persona 简历里都埋了一段)
   - 测:plan-mode 能否问出重点 + 改写能否对齐目标岗位关键能力(老师 痛点 1/2)
2. **第 2 条 — "隐藏亮点段"**(简历里埋了 deal size / 跨部门协调 / 客户级别等学生没强调的细节)
   - 测:AI 改写能否**主动提炼**学生自己没意识到的关键信息
3. **第 3 条 — 同一段 bullet 喂 2 个不同目标岗位**(例:同样的实习给"投研" vs "管培"看)
   - 测:v2 应当**强调不同方面**(投研突出研究框架,管培突出协调能力)— "避重就轻"

**对 P8(红线 persona)额外加 2 条**:
- LightGBM bullet → `warnings` 必须为空(真数字不该误报)
- PVSyst 那段 100 万欧元 bullet → `warnings` 必须 ≥ 1(假数字必须红警)

**通用验证**:
- v2 文本字数 ∈ v0 字数的 [0.8, 1.3](不删太多,不灌水)
- v2 至少 1 处引用 memory 里的具体细节(公司名 / 数字 / 技术名)
- 空 memory 时 v2 应返 `needs_plan_mode=true`
- v2 **不能出现套壳话黑名单**(维度 4 详见)

### Step 7 — 多模块联动(闭环验证)
- 改写采纳后再调 `GET /recommendations`,验证排序有变化(因为 account_memory 更新)
- 在 plan-mode finalize 入档后,再调 `GET /recommendations`,推荐应当也变化

## 3. KPI 指标体系 — 6 个维度,每个维度有具体打分公式

### 维度 1 — 功能上线完整性 (满分 100)

| 指标 | 公式 | 满分 |
|---|---|---|
| 5 个新 endpoint 全部可达 | `(可达 endpoint 数 / 5) × 100` | 20 |
| 5 surface UI 数据流通 | 每 surface 学生侧能读 / 写各 +10 | 50 |
| Demo session 拦截正确 | demo 上 3 个 write endpoint 全 403 +30 | 30 |

**红线**:任何一项 0 分 → 该 persona 整体 fail。

---

### 维度 2 — 推荐深度 (满分 100,**总分权重 × 0.8** — 老师反馈这不是 #1 痛点)

| 指标 | 公式 | 满分 |
|---|---|---|
| 赛道命中率 | top 5 推荐里目标赛道(persona 写明的)占比 | 30 |
| 反向覆盖避免 | persona 反向赛道(明确不想去的)在 top 10 里 < 2 个 | 20 |
| "为什么推" 含金融行话 | LLM 判官扫一遍,引用具体公司业务 / 行业术语的卡占比 | 20 |
| reject 后排除生效 | 反馈过的 job_id 二次拉取不出现 | 10 |
| Memory 更新触发重排 | 加 memory 前后 top 10 至少 2 个位置变化 | 20 |

---

### 维度 3 — AI 记忆有效性 (满分 100)

| 指标 | 公式 | 满分 |
|---|---|---|
| 召回率 | 学生说了 N 条事实,记入档案的条数 / N | 30 |
| 假阳性率 | 抽错(学生没说但 AI 编出来)的条数 / N,**越低越好** | 20(0 错即满分) |
| Category 收敛 | 抽出的 entry 必须 ∈ {experience, skill_claim, preference}(A-4 简) | 15 |
| Dedupe 工作 | 同一事实重复说 3 次,只入档 1 条 | 15 |
| 偏好持久化 | 透露的偏好在 24h 后再拉档案仍存在 | 20 |

---

### 维度 4 — 改写深度 (满分 100,**总分权重 × 1.5** — SAIF 老师眼里的 #1 维度)

老师两位都说学生 top 困惑是**"讲不清实习 / 提炼不出亮点 / 不知道展示哪些能力对齐目标岗位"**。所以维度 4 的子项**完全围绕老师亲口说的痛点**重写:

| 指标 | 公式 | 满分 |
|---|---|---|
| **「提炼亮点」**:同段 bullet,AI 是否点出学生**自己写时忽略的关键信息**(deal size / 跨部门协调 / 客户级别) | 老师 1 痛点 1 | **25** |
| **「避重就轻」**:同段 bullet 给不同目标岗位(投研 vs 管培),v2 应当**强调不同方面** | 老师 1 痛点 1 | **25** |
| **「对齐目标岗位需要的能力」**:v2 体现的核心能力跟目标岗位 JD 的关键能力对得上(LLM 判官对照) | 老师 2 痛点 1 | **25** |
| **Thesis 引用率 + 防套壳话**(见下表) | 之前的 | **25** |

### 套壳话黑名单(每出现 1 条 −5 分,直至该项分数清零)

老师 2 提到的"听起来对其实没意义"类话术,我整理成反向词典:

| 黑名单话术 | 为什么扣分 |
|---|---|
| "建议突出量化结果" | 学生不知道怎么突出,这是废话 |
| "可以补充对宏观经济的理解" | 没具体到行业,等于没说 |
| "面试时要展示行业洞察" | "洞察"两个字最虚 |
| "建议结合具体业务场景" | "具体"=不具体 |
| "突出您的核心竞争力" | 空话 |

AI 改写 / 推荐解释里**每出现 1 条 −5 分**。这是 SAIF "desensitized to DeepSeek 套壳" 那句话的可量化版本。

## 4. 通过 / 失败标准

**总分公式**(反映老师反馈的权重再分配):

```
总分 = 维度1 × 1.0  (功能完整性)
     + 维度2 × 0.8  (推荐深度 — 老师反馈不是 #1)
     + 维度3 × 1.0  (AI 记忆)
     + 维度4 × 1.5  (改写深度 — 老师眼里 #1)
     + 维度5 × 1.0  (Plan-mode)
     + 维度6 × 1.0  (红线,有一票否决)
```

单 persona 满分 = 100 × (1 + 0.8 + 1 + 1.5 + 1 + 1) = **630**

| 等级 | 标准 | 含义 |
|---|---|---|
| 🟢 **PASS** | 维度 1 + 维度 6 满分 · 加权平均 ≥ 75% (≥ 473/630) · 8 个 persona 都 PASS | 可以推生产给 SAIF demo |
| 🟡 **CONDITIONAL** | 维度 1 + 6 满 · 加权平均 60-75% (378-473) · 至少 6/8 persona 通过 | 可推但有改进项 — 列出 finding |
| 🔴 **FAIL** | 维度 1 / 6 有一项不满分 · 或加权平均 < 60% · 或超过 2 个 persona fail | 不可推生产 — 修完重测 |

## 5. 测试怎么跑 — 我会怎么编排

### Phase A — 准备(单 subagent,约 1 小时)
- 写 8 个 persona JSON 文件(`backend/tests/eval/personas/workspace_2026_05_20/P{1..8}.json`)
  - 沿用现有 `touyan_*.json` schema
  - 每个 persona 带 5 个测试字段(沟通风格 / 流水账段 / JD 锚点 / 隐藏亮点 / 想避开想强调)
- 生成 8 份对应的 PDF 简历(用 `pdf_export` service)
- 写 driver 脚本 `backend/scripts/eval_workspace_2026_05_20/`(扩展现有 `eval_full_loop/` 框架)
  - 7 个 step 各 1 个 script + 1 个 run_one_persona.py 串起来
- 跑 1 个 dry-run(P1)验证脚本 work,输出 `_out/P1_report.json`

### Phase B — 跑测(8 个 subagent 并行,worktree 隔离)
- 8 个 subagent 各跑 1 个 persona,worktree 隔离避免互相干扰
- 每个 subagent 走完 7 步,输出 `_out/{persona_id}_report.json`(每步原始数据 + 6 维度初评)
- 预计每个 persona 约 30 LLM 调用,8 个并行约 30-45 分钟 wall time

### Phase C — 评分(2 个 subagent)
- **机器评分 subagent**:跑可量化指标(数 endpoint / 数 entry / 算占比)
- **LLM 判官 subagent**:把推荐 + 改写交给一个独立的 LLM(用 DeepSeek 或 Qwen)扮演"金融审稿老师"盲评维度 2、4、5 里的主观项

### Phase D — 汇总(主 agent 串行)
- 8 persona × 6 维度 = 48 个分数 → 一张矩阵表
- 高亮 fail 项 + 给具体 finding(例:"P2 的 TMT 推荐里有 3 个是销售岗,赛道判断错")
- 输出 `docs/eval-reports/workspace-2026-05-20.md`
- 直接给您"PASS / CONDITIONAL / FAIL + 一句话原因"

**总耗时预估**:Phase A 1h + Phase B 45 min(8 并行) + Phase C 30 min + Phase D 30 min = **约 2.75-3 小时**

## 6. 最终交付给您的东西

1. **一张评分矩阵**(8 persona × 6 维度,每格分数 + PASS/FAIL 标记,带权重总分)
2. **一句话结论**:这版能不能给 SAIF 老师看
3. **Top 5 finding**(按严重度排序的问题列表,每个含"问题 + 复现步骤 + 严重度")
4. **一份 demo-ready 的 transcript**:挑 1-2 个 persona 完整对话流跑出来给您看,作为"AI 给 SAIF 学生反馈" 的样例
5. **套壳话出现频次报告**:5 条黑名单每条在 8 persona × 3 bullet × 2 输出(rationale + v2)= 240 次输出里出现多少次

## 7. 不做什么 — 避免过度工程

- **不做** UI 自动化(Puppeteer / Playwright):本次只测 API + 数据流,UI 渲染靠之前的 build 验证
- **不做** 压测 / 性能基准
- **不做** 真实学生招募(那是 SAIF 试点的事)
- **不动** prod 数据库 — 全在 dev VPS 上跑

## 8. 风险点 + 应对

| 风险 | 应对 |
|---|---|
| LLM 判官评分不稳定(同 input 两次出不同分) | 每个主观项跑 3 次取中位数,差异 > 20 分时人工抽样 |
