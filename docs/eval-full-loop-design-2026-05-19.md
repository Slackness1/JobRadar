# 全链路真实学生验证 — 设计文稿

> 2026-05-19. 目的:对 SAIF 演示前,用强模型 subagent 当"真实学生"和"独立面试官评委",
> 走完 简历修改 → 模拟面试 整条链路,**可证伪地**验证产品质量是否到位.

---

## 一、为什么要做这个

### 想回答的问题(产品视角)

不是「代码里链路是否连通」(那个上次已经验过部分),而是:

> 让一位真实背景的学生从头走完产品 — 系统给他的反馈,**到不到位**?  
> 系统出的面试题,**对不对口、有没有切要害**?  
> 系统是不是真的**记住了这个学生、用上了他的经历**?

### 上次"模板"的局限

上次跑的对照 demo 是个手工模板:学生背景是写死的 yaml,候选人答案是开发拟的一段话,
评分质量是开发肉眼判断的.对 SAIF 老师有 **3 个硬伤**:

| 硬伤 | 影响 |
|---|---|
| 学生是静态画像,不是"活的人" | 没有真实学生那种"答到一半改口"、"想引用经历但说不清"等 corner case |
| 只有 1 道题 | 看不出连贯的面试节奏 — 出题有没有跟着候选人在走、追问有没有切要害 |
| 评分质量是开发说的 | 开发既当裁判又当运动员,SAIF 老师不会买账 |
| 没有简历修改环节 | "AI 帮学生改简历 → 改完的学生再去面试"这条产品主线没体现 |

### 这次要交付的

一份**端到端的实证报告** — 不是开发说哪里好,是**独立评委(强模型 subagent)说哪里好哪里不好**.
报告产出物的形态,SAIF 老师拿到手就能直接评判:

> "这个学生周海,光华金融,中金大消费实习.系统跟他聊了 12 轮,记下了 9 条关于他的事.
> 然后做模拟面试,系统问了他 7 题(题面贴这里),他答了 7 段(答面贴这里),系统给了
> 7 份反馈(反馈贴这里).我们请了 3 位独立评委(资深面试官 + 教学专家 + 产品 reviewer)
> 给整轮面试打分:**问题质量 7.8/10, 反馈到位度 8.2/10, 系统记得这个学生 9/10**.
> 评委的原话评语见附录."

这是 SAIF 老师能看懂、能反驳、能信服的物料.

## 二、整体设计

### 4 个 subagent 各司其职

```
┌─────────────────────────────────────────────────────────────┐
│  Subagent A: Persona Generator (Opus 4.6, 用强模型)         │
│  → 生成一个真实复杂的学生人格(教育/实习/性格/盲点)         │
└─────────────────────────────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────┐
│  Subagent B: Student Chat Agent (Sonnet 4.6)               │
│  → 扮演这位学生跟产品聊 8-15 轮,触发真实记忆写入           │
└─────────────────────────────────────────────────────────────┘
                            ↓
                  [产品的真实链路开始工作]
              chat extractor → account_memory
                            ↓
┌─────────────────────────────────────────────────────────────┐
│  Subagent C: Student Interview Agent (Sonnet 4.6)          │
│  → 同一学生答完整面试 6-8 题(skeleton + follow-up)          │
│  → 答题必须基于自己人格,会有真实学生的 corner case         │
└─────────────────────────────────────────────────────────────┘
                            ↓
              [产品真实链路:出题 + 评分 + 追问]
                            ↓
┌─────────────────────────────────────────────────────────────┐
│  Subagent D: Quality Reviewer (Opus 4.6, 必须强模型)        │
│  → 多角色审查:面试官视角 / 教学专家视角 / 产品视角         │
│  → 给问题质量、反馈质量、链路一致性各打分                  │
└─────────────────────────────────────────────────────────────┘
                            ↓
                  最终交付报告 markdown
```

### 为什么 Subagent A 和 D 必须用 Opus 4.6

- **A (生成学生)**:学生人格要真实有血肉(不是简历包装版,有缺陷有口头禅),弱模型会
  产出扁平的"模范学生" — 反而盖住产品的真实表现.
- **D (评委)**:这是整个 demo 的**裁判**.弱模型评委会放过劣质输出,反而给产品虚高的评分,
  到 SAIF 现场被老师当场拆穿.必须用最强模型当 judge.
- B、C 用 Sonnet 4.6 是 cost vs quality 平衡 — 学生扮演不需要顶级智商,稳定输出即可.

## 三、4 个 Subagent 的具体行为

### Subagent A — 学生人格生成器

**输入**:1 个 scenario 配置,3 个维度
- 目标赛道:`二级买方·基本面` / `量化` / `卖方研究` / `一级 PE` 任选
- 学生 tier:`强` (Top 校 + Top 实习) / `中` (普通 985 + 一段相关实习) / `弱` (双非 + 实习薄)
- 跨专业标志:是否非金融背景转金融

**输出**:1 份学生人格 JSON,包含
- **简历内容**:教育、3 段实习(每段含 4-6 条 bullet)、2-3 个项目、技能、奖项
- **真实背景细节**:每段实习的"实际做了什么 + 没做什么 + 留下哪些坑"
  (这些细节不写在简历里,但会在 chat 里慢慢露)
- **性格特征**:口头禅、答题习惯、紧张时会怎么样
- **盲点**:这个学生**自己看不见**的短板(供评委后面评判:产品有没有帮他看见)

**反例约束**:
- 不允许生成"光鲜模板生" (例: 北大 + 高盛 + 中金 + CFA 三级 + 红圈所)
- 必须有至少 2 个**真实学生会有**的"灰色地带":
  - 实习里有段时间是凑数性的(打杂、做 PPT、没参与核心建模)
  - 某段经历里有可量化的失败 / 妥协(项目最终没成、自己看不出哪步出错)

**实现思路**:Persona generator 用 Opus 4.6 跑一次,产出固化为 fixture JSON.
不同 scenario 跑出来的人格存到 `tests/eval/personas/` 里复用,**不**每次重生成
(否则跨次跑无法对照).

---

### Subagent B — 学生 chat 行为模拟

**目的**:让产品的记忆写入路径**真的被触发** — 上次实测 4 段陈述只攒下 1 条记忆,
这次要测「正常用户 10-15 分钟聊出来能攒多少」.

**输入**:Subagent A 产出的人格 JSON + 产品的 resume copilot chat 入口
(每次发送 user 消息后,等系统响应、记忆抽取完,再发下一句).

**行为约束**:必须像真实学生
- 不会一次说完所有事(分多轮挤牙膏)
- 会被产品的追问引导(产品问"你这个项目具体做了什么",学生才详细展开)
- 会问反问句("我这种背景投基金行业研究有戏么")
- 会自我修正("不对,刚才说错了,其实是...")
- 会犯小错(把日期记反、把岗位记岔)

**轮数目标**:8-15 轮,直到记忆采集饱和(连续 3 轮提取不到新记忆为止).

**数据采集**:
- 每轮 user 消息
- 系统响应
- 该轮触发的记忆写入结果(几条新、几条更新、几条被拦)
- 最终 account_memory 表的快照

**成功标准**:`account_memory` 表里这个 user 至少有
- 4 条 `experience` 类
- 2 条 `skill_claim` 类
- 1 条 `preference` 类
- 1 条 `identity_fact` 类

**如果没达标**:在报告里**显式标注「提取器漏采率 X%」**,反过来用做产品反馈
(这个数据上次跑就发现是个产品问题).

---

### Subagent C — 学生面试行为模拟

**目的**:产品的面试模块拿到「这是周海(背景如下)」之后,出题 + 评分能不能贴着他走.

**输入**:同一份学生人格 JSON + 已经填好的 account_memory + 产品的面试入口.

**面试设置**:
- 目标岗位:跟 Persona 里的"目标赛道"对应(用真实 JD,例:嘉实股票行业分析师)
- skeleton 6 题(产品默认)
- 期望追问 8-12 次(产品的 adaptive picker 决定)
- 学生用语音转写的方式答(模拟真实学生答题节奏 ─ 偶尔卡顿、改口)

**学生答题约束**(关键 — 这是这次测试的核心约束):
- 答题内容**必须从 persona 里取材**,不能凭空编(否则面试就成了"两个 LLM 互相聊")
- 每题答 200-400 字
- 至少 2 题里"刚好可以引用某段实习但学生没主动提" — 用来测产品的 personalization
  能不能识别这种"该用没用"的场景
- 至少 1 题里"故意答错某个 technical 细节" — 用来测产品评分能不能抓住
- 至少 1 题里"答完主动反问" — 用来测产品 chat-style 处理能力

**数据采集**:
- 每题: 题面 / 学生答案 / 产品评分 / 追问(如有)
- 整轮面试结束的 report(若产品有这个能力)
- 期间触发的每一次 ContextProvider fetch(用 LLM_CTX_TRACE log 抓)

---

### Subagent D — 多视角质量评委

**目的**:不是开发说好,是**独立强模型评委**说好.评委本身**不知道**这个学生是
生成出来的、不知道答题是 LLM 模拟的 — 只看产品的输出.

**4 个视角**(每个视角独立 invoke,避免相互锚定):

#### 视角 1: 资深面试官 — 问题质量

**评判**:
- 题目是否对口岗位(行业研究员问 DCF 是对口的,问 "讲一个机器学习项目" 不是)
- 追问有没有切要害(候选人答了空话,系统该追"具体说说量化的部分"而不是放过)
- 追问有没有跨经历跳跃(候选人在聊 A 实习,系统不该突然问 B 实习)
- 追问深度:第 2-3 层是否到位还是浮在表面

**输出**: 0-10 分 + 5 条具体证据(哪几道题好/差,引用题号)

#### 视角 2: 资深面试官 — 反馈质量

**评判**:
- hits/misses 准不准(候选人确实答了的算 hit,确实漏的算 miss)
- 有没有空话标签("结构清晰" / "缺业务痛点" 这种但缺乏具体引用)
- **personalized 信号**:miss 里有没有引用学生具体经历 / 上次反馈 / 熟练工具
  (这是 C' directive 想要的效果)
- 评分(overall)合不合理:答得空泛的题没给 30-40,答得到位的题没扣分

**输出**: 0-10 分 + 每题反馈逐题点评

#### 视角 3: 教学专家 — 学生进步可能性

**评判**:
- 这套反馈帮学生看见了哪些 **他自己看不见** 的盲点(对照 Persona 里的"盲点"字段)
- 反馈是否可执行(说了什么具体可以改进、不是抽象建议)
- 整轮面试结束,学生**离面试通过近了一步**吗?

**输出**: 0-10 分 + 学生收获的具体 takeaway 列表

#### 视角 4: 产品 reviewer — 链路一致性

**评判**:
- chat 里学生说过的内容,面试出题有没有用上
- chat 里学生说过的内容,面试反馈有没有用上(personalization 命中率)
- 同一段经历(例:中金白酒实习)有没有在多个题里被一致引用 / 还是被遗忘了
- 出题先后顺序是否符合"由浅入深"

**输出**: 0-10 分 + "系统懂这个学生" 的具体瞬间清单 / 反例清单

## 四、产出物

### 单个 scenario 的最终报告

`docs/eval-full-loop-reports/{scenario_id}-{date}.md`

结构:
1. **学生 persona 卡片**(Subagent A 输出,简历 + 真实背景细节 + 盲点)
2. **简历修改 chat 记录**(Subagent B,完整 12-15 轮对话 + 每轮记忆写入快照)
3. **记忆库快照**(产品里实际写入 account_memory 的内容,分类列出)
4. **完整面试 transcript**(Subagent C 的答 + 产品的题 + 反馈,共 6-8 题)
5. **4 视角质量评委报告**(Subagent D 输出,每个视角独立打分 + 评语)
6. **链路一致性证据**("系统懂学生"的高光时刻 vs 系统遗忘的低谷时刻)
7. **汇总评分**(4 视角加权,得出总分,以及与上次/不同 scenario 对照)

### 多 scenario 对照矩阵

跑完 3 个 scenario(强配对 / 中配对 / 跨专业弱配对)后,做一张对照表:

| 维度 | 强配对(光华+中金 IB→嘉实研究员) | 中配对(普通 985→公募) | 跨专业(CS→金融) |
|---|---|---|---|
| 问题质量 | x.x | x.x | x.x |
| 反馈质量 | x.x | x.x | x.x |
| 教学价值 | x.x | x.x | x.x |
| 系统懂学生 | x.x | x.x | x.x |
| **总分** | x.x | x.x | x.x |
| **被指出的最强短板** | ... | ... | ... |

这张表给 SAIF 老师看时,可以**直接证明**"产品对不同 tier 的学生表现稳定/有差异",
而不是开发口头说"我们都覆盖到了".

## 五、执行计划

| Phase | 内容 | 工期 | 关键产出 |
|---|---|---|---|
| **Phase 1** | Persona Generator (Subagent A) + 1 个 scenario fixture 固化 | 1 天 | `tests/eval/personas/{scenario_id}.json` |
| **Phase 2** | Student Chat Agent (Subagent B) + 真实 chat 跑 1 个 scenario,验证记忆采集率达标 | 1 天 | chat transcript + 记忆快照 |
| **Phase 3** | Student Interview Agent (Subagent C) + 跑完 6-8 题 | 1 天 | 面试 transcript |
| **Phase 4** | 4 视角 Quality Reviewer (Subagent D) + 第 1 份完整报告 | 1 天 | 第 1 个 scenario 完整报告 |
| **Phase 5** | 扩到 3 个 scenario + 对照矩阵 | 半天 | 多 scenario 矩阵 |

**总计**:~4.5 工作日.

### 中期里程碑

- **Phase 1+2 跑完 (Day 2)** 拍一次 — 看记忆采集率是否真的能上 8 条.如果还是只能抓
  1-2 条,**先停下来改提取器**,再继续往后跑(否则 Phase 3 起点就错).
- **Phase 4 跑完 (Day 4)** 跟你过一次完整报告 — 看 Reviewer 的评语像不像 SAIF 老师
  会写的,如果太"AI 化"再调 prompt.

## 六、风险 + 已知短板

| 风险 | 应对 |
|---|---|
| LLM 跑一次完整链路 cost 高(Opus 4.6 评委尤其贵) | 单 scenario 预算 ~$8-15.先跑 1 个 scenario 验完整,再扩;不要一上来跑 5 个 |
| Subagent 是 LLM 模拟,不是真人 → 有些 corner case 抓不到 | 在报告里**显式标注**:"这是 subagent 模拟,真实学生还会有 X、Y 风险" |
| Reviewer 自己也是 LLM,可能给虚高分 | 用 4 视角独立 invoke 取平均;严格 prompt 要求"必须引用具体证据,不准空话好评" |
| 记忆采集率太低导致 Phase 3 起点弱 | Phase 2 设硬门槛(至少 8 条 memory),不达标先修产品 |
| 产品某条分支今天有 bug | 把 bug 记下,在报告里如实写,不掩盖 |

---

## 七、跑完之后用来干什么

1. **SAIF 演示物料**:报告本身 + 那张对照矩阵就是核心 demo 内容
2. **产品迭代依据**:Reviewer 指出的问题清单,直接转 backlog
3. **回归测试**:每改一次产品,重跑同一个 scenario,对比新旧报告
   (这是 SAIF 老师特别会问的 — "你们改了之后怎么知道没退步")
4. **对外讲故事**:报告可以脱敏后作为 case study,投给合作方

## 八、跟之前已有工作的关系

- `docs/eval-touyan-v1-design.md` 的 eval harness 是**单题**评分对照,跑得快,适合
  pytest 集成.这份新设计是**单学生完整面试链路**,跑得慢,适合 demo / 回归.两者互补,
  不替代.
- `tests/eval/fixtures/touyan_v1/` 的现有学生 fixture 是手写的,这次会用 Subagent A
  **替换**(更真实).现有 fixture 保留作为简单回归用.

## 九、要不要按这个设计开干

待你定的 3 件事:
1. 起点 scenario 选哪个 — 推荐 **二级买方·基本面 + 中配对学生** (强配对说服力不够,弱
   配对又显得我们故意找简单题)
2. Subagent A/D 用 Opus 4.6 cost 你能接受吗 — 单 scenario 完整跑预算 ~$10-15
3. 整段 4.5 天工期,是连续跑完,还是先 Phase 1+2 验证记忆采集再决定要不要继续

按你的选择,Phase 1 我马上可以开干.
