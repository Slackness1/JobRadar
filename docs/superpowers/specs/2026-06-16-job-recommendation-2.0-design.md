# 岗位推荐 2.0 — 可追踪、会轮换的岗位流（设计稿）

> 状态：设计稿，待 review。本文只定形态与边界，详细实施步骤进后续的实施计划。
> 业务背景：SAIF 2026 秋招试点。学生在简历副驾驶里拿到岗位推荐后，要能"持续用得下去"——
> 不是看一眼就完事，而是能标记、能追踪投递进度、每次进来都有新岗位看。

## 一、为什么要改（现状的三个痛点）

读现有推荐链路（`recommendation.py` / `recommendation_v2/` / `routers/resume_copilot.py`）后确认：

1. **一次性、量小、不轮换**：推荐结果一次性存成一条 run（`resume_recommendation_runs`，每个会话唯一一条），
   校招 + 实习两流各取 ~10，最终给前端约 20 条。生成后没有"换一批"、没有翻页、没有重排。
   学生反复进来看到的就是同一批，候选召回池其实有约 100 条，但绝大多数永远不会被看到。
2. **没有"看过"概念**：系统不记得学生看过哪些岗。无法做"下次优先推没看过的"，也就无法轮换。
3. **岗位级状态只有"拒绝"一种**：现在唯一的岗位级动作是"不喜欢/拒绝"（写 `rejected_job_ids_json` +
   account_memory）。没有"收藏/想投""已投递"这类正向标记，更没有投递全生命周期的追踪。
   学生标记完投递后，系统拿不到任何反馈，"投了没"是个黑洞。

→ 结论：缺的不是推荐算法，是**岗位级状态层 + 轮换调度 + 一个聚合视图**。

## 二、目标与非目标

**目标（MVP）**
- 打破"约 20 条上限"：让学生能持续翻到更多没看过的岗（用满约 100 条召回池），并能"换一批"。
- 岗位级三态标记：收藏/想投、已投递、不合适——覆盖投递全生命周期的主干。
- "我的岗位"汇总页：按状态分组，一眼看到投了几个、想投几个。

**非目标（本期明确不做，避免范围蔓延）**
- **不做偏好学习**：不根据"收藏/已投/不合适"反向调整推荐排序或权重。标记纯做追踪，不回流到算法。
  （这是和学院"可证伪反馈"对齐的克制选择：先把骨架做扎实、上线见效，智能学习排下一轮。）
- 不做面试进度、offer 结果等更细的生命周期分期（"已投递"不再细分到"笔试/面试/oferr"）。
- 不动 v1/v2 推荐生成算法本身（召回、打分、rerank 逻辑保持不变）。
- 不做跨会话的岗位状态合并 UI（状态按 user_key 存，天然跨会话，但本期不做"会话切换提示"）。

## 三、整体形态

三块拼起来：**① 岗位状态层（数据）→ ② 轮换调度（服务）→ ③ 三处 UI（标记按钮 + 换一批 + 我的岗位页）**。

### 3.1 岗位状态层（新增一张表）

新增 `resume_job_user_state`，按 **(user_key, job_id)** 唯一，跟随用户跨会话——投递追踪是"人"的属性，
不是某次会话的属性。

| 列 | 说明 |
|---|---|
| `id` | PK |
| `user_key` | 用户稳定标识（`u_%d`），与 account_memory 一致 |
| `job_id` | 对应 `jobs.job_id` |
| `state` | 枚举：`seen`（看过，自动）/ `saved`（收藏想投）/ `applied`（已投递）/ `dismissed`（不合适） |
| `first_seen_at` | 首次出现在该用户推荐流里的时间（用于轮换排序） |
| `state_updated_at` | 最近一次显式标记时间 |
| `source_session_id` | 标记发生时所在会话（仅追溯用，不参与唯一约束） |
| `created_at` / `updated_at` | 标准时间戳 |

设计要点：
- **`seen` 是隐式状态**，由"岗位被实际下发到前端推荐流"时自动写入（见 3.2），学生无感。
- **显式三态互斥**：`saved` / `applied` / `dismissed` 同一岗位同一时刻只有一个；学生改主意可在三者间切换，
  或撤回到无显式状态（仍保留 `seen`）。
- **`dismissed` 收编现有"拒绝"流**：现在的 `rejected_job_ids_json` + reject 端点继续工作并双写到本表的
  `dismissed`，前端逐步统一到本表；不破坏既有拒绝行为（理由字典、写 account_memory 不变）。
- 唯一约束 `UniqueConstraint(user_key, job_id)`；状态变更走 upsert。
- 新表只走 Alembic migration，`inspector.get_table_names()` 做幂等检查（遵守后端铁律）。

### 3.2 轮换调度（会轮换的岗位流）

核心思想：**把"一次性 20 条结果"变成"对一个更深的已排序候选池做分页 + 排除看过"**。

- **生成阶段**：推荐生成时，把召回 + 打分后的**完整有序候选池**（最多约 100 条）的 `job_id` 列表 + 分数
  持久化（存进 run，或与 run 关联的轻量表）。**这一步不改打分/rerank 算法**，只是把"砍到 20"改成"留全量有序池"。
- **下发阶段（GET 推荐 / 换一批）**：服务端从有序池里，**跳过该 user 已 `seen` / `dismissed` 的 job_id**，
  取下一页（约 12 条）返回，并把这一页 job_id 标记为 `seen`。
- **"换一批"= 取下一页**：纯翻页，advance 到池子里下一段没看过的，不重新跑生成（避开 7 分钟生成延迟）。
- **LLM 推荐理由按需补**：现在 LLM rerank/narrative 只覆盖前 10。轮换后改为**对"即将下发的这一页"按需生成并缓存**
  （结果写回 run 的 item，缓存命中不重复调用）。首屏 + 下一页可预生成，让"换一批"基本秒回。
  → 依赖：v2 rerank/narrative 的并行化（见 `docs/.../specs` 里 latency 修复计划，属相关前置工作）。
- **池子见底兜底**：当没看过的岗位取完，回收 `seen`（按 `first_seen_at` 最旧优先）重新展示，
  并在前端给一句"你已看完目前所有新岗位，以下是之前看过的"——不静默假装还有新岗（遵守"不静默截断"原则）。

### 3.3 三处 UI

1. **推荐卡上的三态标记**（`RecommendCard.tsx`）：在现有展开/拒绝交互旁，加"收藏想投 / 已投递 / 不合适"三个动作。
   `不合适` 复用现有拒绝表单（带理由）；`收藏`/`已投` 一键切换，乐观更新。卡片上显示当前状态徽标。
2. **"换一批"入口**（右栏 feed 底部）：点一下取下一页未看过的岗；池子见底时按钮文案切换为"重看之前的岗位"。
3. **"我的岗位"页**（新路由，如 `/my-jobs` 或工作台内一个 tab）：按 `saved` / `applied` 分组列出，
   顶部一行进度概览（想投 N / 已投 M）。`dismissed` 默认折叠，可展开"我屏蔽的岗位"以便撤回。

## 四、API 表面（新增/改动）

| 端点 | 方法 | 作用 |
|---|---|---|
| `/sessions/{id}/recommendations` | GET（改） | 返回当前页（排除已看过），并把本页标记 `seen` |
| `/sessions/{id}/recommendations/next-batch` | POST（新） | "换一批"：advance 到下一页未看过的岗 |
| `/jobs/{job_id}/state` | POST（新） | 标记 `saved` / `applied` / `dismissed`，或撤回；按 user_key upsert |
| `/my-jobs` | GET（新） | 按状态分组返回该 user 的岗位状态 + 进度计数 |
| `/sessions/{id}/recommendations/{job_id}/reject` | POST（保留） | 现有拒绝端点继续工作，内部双写到 `dismissed` |

约束：所有写端点加 `_assert_not_demo`（demo 会话只读铁律）；状态写入按 `user_key` 鉴权（X-Resume-User-Key）。

## 五、兼容与迁移

- **demo 会话**：`__demo__` 只读，标记端点对其返回 403；轮换对 demo 走"固定首页"不写 `seen`，保持示例稳定。
- **既有数据**：上线时存量 `rejected_job_ids_json` 一次性回填到 `resume_job_user_state` 的 `dismissed`（迁移脚本，幂等）。
- **flag 控制**：整个 2.0 行为挂一个 flag（如 `RECOMMENDATION_ROTATION_ENABLED`），默认关 = 与现状字节级一致，
  灰度开（遵守 strangler-fig 风格，可单账号灰度）。

## 六、测试要点

- 单测：状态 upsert 互斥（saved↔applied↔dismissed 切换 + 撤回）、唯一约束、demo 403。
- 单测：轮换分页排除 `seen`/`dismissed`、池见底回收顺序（`first_seen_at` 最旧优先）。
- 集成：连续两次"换一批"返回不重叠的未看过岗；reject 端点双写到新表。
- 端到端：标记 saved/applied → "我的岗位"分组与计数正确。
- 回归：flag 关闭时推荐输出与现状一致（diff 为空）。

## 七、待确认 / 风险

1. **池子深度**：召回池约 100，是否够"持续轮换"的体感？若不够，是否允许放宽召回窗口（>30 天）。MVP 先用现有池。
2. **"我的岗位"落点**：独立路由 vs 工作台内 tab——倾向工作台内 tab（少一次跳转），但需确认 hub 壳布局能容纳。
3. **换一批的 LLM 成本**：按需生成下一页 narrative 会增加调用；需确认并行化 latency 修复先落地，否则换一批会卡。
4. **状态与"拒绝学习"的边界**：本期 dismissed 仍写 account_memory（既有行为），但**不**让 saved/applied 进 memory——
   确认这条边界，避免无意中把"追踪"变成"学习"。
