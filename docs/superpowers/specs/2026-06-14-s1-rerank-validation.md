# S1 实验 5 — 精排能否清掉召回侧跑偏(2026-06-14)

> 问题:dense 召回那 19.6% 跑偏,是精排的输入还是用户的输出?对 72-query eval set 的 dense top-12
> 跑一遍"相关性精排",看首屏(off@5)跑偏被压到多少。
> 精排器:**sonnet-4.6 subagent**(12 个并行,每 persona 一个)。选 sonnet 而非生产 deepseek-pro 的原因:
> ① 生产 OpenCode key 对批量 pro 硬限流(0.05/s,跑不动);② sonnet 对 deepseek-flash 判官跨厂商,
> 避开自评循环,反而更干净。这是"一个称职的相关性精排器能做到什么"的公平代理。

## 结果:dense → dense+精排

| 分段 | nDCG@10 | off@5(首屏跑偏) | off@10 |
|---|---|---|---|
| 全体(72) | 0.641 → **0.752** | 9.4% → **3.9%** ✅ | 13.3% → 9.9% |
| 金融(48) | 0.576 → 0.690 | 12.1% → **5.0%** ✅ | 16.9% → 13.5% |
| 互联网(24) | 0.772 → 0.878 | 4.2% → **1.7%** ✅ | 6.2% → 2.5% |

## 结论

1. **精排把首屏跑偏清干净了。** 三个分段的 **off@5 全部 ≤8% 红线**(金融 12.1%→5.0%、互联网 1.7%)。
   召回侧那 19.6% 跑偏确实是精排的输入,精排把它们顶出了首屏 —— **反转 B 成立**。
2. **nDCG 还顺带涨**(0.64→0.75):精排同时改善了排序质量。
3. off@10 改善较弱(金融仍 13.5%):清洗集中在 top-5。但首屏(top-5)是学生主要感知,off@5 达标即可上线。

→ **S1 dense 召回 + 相关性精排 = 可上线的两段式架构。** 召回管覆盖(recall 25%→58%),精排管首屏精准(off@5 ≤8%)。

## 一个必须落地的前提(否则 prod 拿不到这个结果)

现有生产精排 `rerank_one` 是 **KB-gated**:只对 sub_cat 有知识库的岗调 LLM,**NULL/无 KB 岗直接返中性 50(不精排)**。
本实验的 sonnet 精排是**对每个候选都打相关性分**。dense 召回里约 26% 是 NULL/无 KB —— 这部分在现有
prod 精排下不会被清洗。**所以要复现这个结果,精排必须升级成"对所有候选打相关性分",而不是只给 KB 覆盖的岗打。**
(74% 有 KB 覆盖,改动是给剩下 26% 加一条不依赖 KB 的相关性兜底打分。)

## 落地架构(收口最终形)

```
召回:dense + sub_cat 软降权(无 sub_cat 硬闸)          ← recall 58%,覆盖互联网+弱enrich段
  ↓
精排:相关性打分(KB 有就用 KB,没有走通用相关性兜底)     ← off@5 压到 ≤8%
  ↓
展示:强匹配 / 可迁移 / 探索 三栏(可迁移岗诚实单列)     ← 把 off@6-10 的擦边岗honestly安置
```

flag `HYBRID_RECALL_ENABLED` 仍默认 OFF,接线 + 精排兜底改造 + 三栏展示做完,用这套 eval 重测
off@5 三段达标 → 翻 flag。
