Decision 01 · Agent Architecture

简历解析：单次 prompt 还是 ReAct Agent？

上下文 · Context

应届生简历格式杂乱（PDF / docx / 扫描件），需要做"读 → 抽结构 → 匹配公司库 → 推断目标" 四件事。 单次 prompt 全做完会幻觉、漏字段、且单点失败无法定位。这不是"模型够不够强"的问题， 是步骤之间该不该可观测的问题。

选项 · Options
A · 单次 long prompt——简单，但易幻觉、出错无法定位弃
B · 4 个独立 prompt 串联——可控，但缺上下文弃
C · ReAct loop + 4 个 tool（read_pdf / extract / match / infer）选
我选 C · 因为
  1. 每一步失败都能精准定位——读 PDF 挂了切 OCR 兜底，匹配挂了切规则兜底；
  2. 每一步耗时可单独优化，不被最慢一环拖死整条链路；
  3. 用户能看到 trace（连接到判断 5 的透明度设计），把"AI 在干什么"显形给信任度敏感的用户；
  4. 串联结构天然支持fallback——这是 PM 在选 AI 架构时最容易忽略、却最值钱的属性。
ReAct Loop · 4 个 Tool
🔍 read_pdf
PDF / docx 解析为纯文本，含位置元数据
→ raw_text · sections
📄 extract_sections
教育 / 实习 / 项目 / 技能 结构化抽取
→ Profile{}
🏢 match_companies
公司名归一化，对齐内部公司情报库
→ company_ids
✅ infer_targets
从经历推断目标方向 + 优先级
→ target_roles
验证 · 数据 / 反馈

字段无需用户纠正比例 87%，4 步独立可调试， read_pdf 失败率 3% → 自动切 OCR 后降到 0.4%。
平均解析 P50 6.4s——比单次 long prompt 慢 1.2s，但可观测带来的故障定位收益远超延迟代价。

Decision 02 · Model Strategy

不是"选一个最好模型"，而是 在不同环节匹配不同模型

上下文 · Context

中文场景 + 应届生用户对延迟敏感 + 内测预算有限。

B · 全程国产单模型——省心，但有任务不擅长弃

Decision 03 · Recommendation Pipeline

Top 5 推荐：纯 LLM 暴力搜，还是 4 层漏斗？

上下文 · Context

岗位库万级，给每条都跑 LLM 不现实（成本 / 延迟劝退）； 但纯规则又太死板，捕捉不到"应届补招、量化分析岗"这类语义匹配。

选项 · Options
A · 纯 LLM rerank 全表——pricing 直接劝退弃
B · 纯规则打分——快但僵、错失语义匹配弃
C · 4 层漏斗：SQL 粗筛 → 规则 → 情报 → LLM 重排选
Architecture · 4 层漏斗

SQL 粗筛

10K → 200
~50ms

200 → 200
~120ms

情报增强
snapshot boost · 公司情报库（融资、团队规模、近期招聘体量）
200 → 200
~600ms

LLM 重排（DeepSeek）

我选 C · 因为

每层只干一件擅长的事 + 每层都有 fallback。SQL 把万级压到 200，规则排出 Top 20，LLM 只对 5 条重排—— LLM 调用降到 1/2000，但语义匹配的好处全保留。

验证 · 成本对照

Decision 04 · Resume Rewrite

AI 改写：套固定模板，还是 按 JD 反向挑用户的卖点？

上下文 · Context

应届生简历"什么都想写"，但 HR 半秒看完只扫 JD 相关关键词。改写不能"通用美化"——必须按这个具体岗位 去挑用户简历里最对得上的证据，而不是给用户再"装饰"一遍。

选项 · Options
A · 3 个固定方向（强量化 / 强因果 / 强影响）——太死板弃
B · JD-driven 反向匹配 + 量化数字加强选
C · AI 完全自动改——失控 + 改飞弃
JD-Driven 匹配示意 · 字节跳动 · 数据分析
目标 JD 关键词
A/B 实验设计与分析
Python · SQL · 数据建模
推动业务决策的项目影响
反向匹配
挑命中证据
非通用美化
用户简历段落（命中加亮）
蚂蚁金服风控 · 主导 A/B 实验 380+ 次
✓ 直接命中"A/B 实验"
Python + LightGBM 风控建模
✓ 命中"Python · 数据建模"
实验结论上推 → 策略调优 ROI +14%
✓ 命中"推动业务决策"
我选 B · 因为

HR 决策窗口是"JD 关键词命中率"——AI 必须从 JD 反推回去挑证据，不能 generic。 互联网岗位重数字 + 项目影响力；研究 / 战略岗位重方法论 + 推理路径；工程岗位重技术栈 + 系统设计。 因岗而异，不一刀切——这恰恰是 AI 比固定模板的关键优势。

Decision 05 · Trace Visibility

AI 黑盒还是开盒？
给用户看推理过程的 代价是什么

上下文 · Context

LLM 推理过程对懂的人是"信任凭证"，对不懂的人是"信息过载"。 完全不显被怀疑"AI 是不是瞎推"，默认展开实时打印又把小白吓跑。这是个受众不一致的设计题。

选项 · Options
A · 完全不显——被怀疑"AI 在瞎推"弃
B · 默认展开实时打印——懂行的爱、小白蒙弃
C · 折叠默认隐藏 + 终端风格实时打印选

AI 时代，PM 的工作变成了什么样

我从 JobRadar 学到的 3 件事
01. AI 时代，PM 的判断比执行更值钱。

4 层漏斗的架构判断是我做的，代码是 AI 写的。多模型策略的取舍是我做的，集成是 AI 写的。 判断"什么值得做、为谁做、做到什么程度"是 PM 的护城河——这件事 AI 反而帮不上忙。

02. AI 不是答案，是放大镜。

我以为 AI 推荐 + 改写就是产品的答案。结果 300 个用户的数据告诉我，真问题在投递信心。 AI 让你 80 分容易做到，但同时把"用户真正卡在哪"暴露得无处可藏。PM 不能再靠"我以为"——必须正视数据反过来打脸的判断。

03. 速度 × 判断质量 = 新的 PM 方程式。

6 周、300 用户、5 个 ship 出去的判断。不是因为我快，是因为 AI 把"试错成本"降到了零。 PM 的工作变成：生成假设 → AI 快速 ship → 看数据 → 调整下一个假设。对错不再是问题，迭代速度才是。

我作为 AI PM 的工作方式
判断 · 执行分离

我定义问题、做取舍、判断 AI 输出好坏；AI 负责把判断变成代码、设计、文案。

快循环

1 周原型 → 1 周用户测试 → 改判断。不写 200 页 PRD，写 5 个判断 + ship 出去看反应。

数据先于直觉

每个判断都预设一个"如果错了我会看到什么"——准备好被打脸，比假装永远对值钱。
